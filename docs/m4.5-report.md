# M4.5 report: quality gates and epics (local)

Status: **done; real-agent eval passed 2026-11-06; merged in PR #8 on 2026-11-06.** It was built on 2026-11-05 on `m4-5-quality-gates`, in three phases. The same branch carries a cleanup pass over `requirements.md` that came before M4.5.

The owner added M4.5 before M5 after asking three questions:
1. Is Sir Codes-a-Lot's code checked?
2. Is there a security pass?
3. Can a technical doc turn into tickets?

The answers were: mostly; partly; no. M4.5 closes each gap with the smallest change that does the job.

**Done when:**
- a branch that fails its own tests goes back to Sir Codes-a-Lot before review;
- Nancy runs the security skill;
- an epic's accepted proposals land in Backlog as linked children.

All three are covered without API calls. Whether the real agents use the new prompts well is the real-agent eval's job, and it passed on 2026-11-06 (see "Real-agent checks").

## What you can do

- **Trust that Code Review only sees branches that build and pass.** After Sir Codes-a-Lot reports success, Kanbot runs the project's build, lint and test commands itself. If one fails, he goes again at once, with the output as a test report. Nancy never sees the branch until the checks pass.
- **Get a real security review.** Nancy runs Cloudflare's security-audit skill on every code diff. A vulnerability the branch introduces goes back to Sir Codes-a-Lot as a blocking comment, with the fix and a regression test to add.
- **Turn a doc into tickets.**
  1. Create a ticket of type `epic`. Paste the doc into its description, or write "Plan from `docs/spec.md` §4".
  2. Move it to Planning. Plan B proposes up to 30 tickets in build order.
  3. Tick the ones you want and click Accept. They land in Backlog as the epic's children, with criteria, touch sets and confirmed "blocked by" links. The epic card shows `2/5 done`.

## How to run it

As in M4: `pnpm db:migrate` (one new migration, `0008_epics`), then `pnpm dev`. Nothing new to configure.

## What was built

- **Phase 1: the checks gate.**
  - `runChecks()` (`apps/worker/src/worktree.ts`) runs build, lint and test in the worktree after a successful In Progress run. It uses the worker's own command runner: the same scrubbed environment as install, and a 10-minute timeout per command.
  - On a failure the run ends `changes_requested`, with the error "Kanbot checks: `<command>` failed". The last 200 lines of output are stored as a `test_report`, which Sir Codes-a-Lot's next run sees as `<latest_test_report>`.
  - In the transition table, `in_progress` + `changes_requested` stays in place. `AfterRun.rerun` makes `finish()` queue the same agent again in that column, resuming his session, with bounce +1.
- **Phase 2: the security pass.**
  - `plugins/security-audit/` is Cloudflare's `security-audit-skill`, pinned at `c1c8a8c` (MIT), reshaped into one skill, `security-review`. Why it was reshaped is under Key decisions.
  - Nancy loads it, and her security check runs it on every diff that changes code.
  - There is a 5th golden ticket, `security`, whose owner hint invites stored XSS.
  - `pnpm eval:agents` now compares totals only over the tickets the baseline has, so adding a golden ticket doesn't fail the 25% bar on its own.
- **Phase 3: epics.**
  - Schema: `tickets.parent_id`.
  - `proposedTickets` in the `report_result` schema. The worker drops duplicate refs and forward or self `blockedBy` refs, so there are no cycles, and stores the list on the plan artifact's `data`.
  - Plan B: an "Epics" prompt section and an epic task line in the context.
  - `POST /api/tickets/:id/accept-proposals`, built on `insertTicket()`, which was split out of `createTicket` so that everything happens in one transaction.
  - A 409 `epic` when an epic is moved into a build column.
  - The epic panel in the drawer, the `n/m done` count on the card, and "part of KEY" on a child.

## Key decisions

- **The gate is the worker's, not an agent's.** It costs nothing and is deterministic, and it uses the same commands Sir Codes-a-Lot is already told to run. A second agent re-running them would only repeat Testy. The gate catches what he skipped or got wrong.
- **A gate failure counts as a bounce.** Without that, a build that never passes would loop forever. The bounce limit sends it to Blocked like any other loop.
- **The skill is one file, not the upstream folder.** The permission hook only lets agents read inside their working directory, so Nancy couldn't open companion files under `plugins/`. Widening the fence to plugin folders would loosen the security boundary to save a copy-paste.
  - So `SKILL.md` is a short Kanbot header for diff review, followed by the upstream core principles, anti-patterns, attack classes, and the web and client-side companions, verbatim (`VENDORED.md`).
  - The full audit mode was left out. It needs parallel sub-agents, writes report files outside the repo, and requires an OS sandbox before it runs target code. None of that fits a read-only reviewer.
  - The skill adds about 11k tokens when Nancy runs it.
- **Epics come from the M6 design, pulled forward.** "A doc into tickets" and "split an epic" are the same mechanism. A doc either goes in the description (50,000 characters) or stays in the repo for Plan B to read. That covers the owner's 94 KB spec without new storage.
- **Accepted links are confirmed.** The owner accepted the plan that names each dependency, so asking again would be an extra click per ticket.
- **Proposals live in the plan artifact's `data`, not a new table.** A revised plan carries its own list. `data.accepted` records what was already created, so a ref is never created twice.

## What was left out on purpose

- **Reading a doc that's neither in the description nor in the repo** (an upload, a URL). Paste it in, or commit it. An upload would need artifact storage for files, and nobody asked for that yet.
- **Nested epics.** Proposals can be `feature`, `bug` or `chore`, not `epic` or `spike`.
- **Clearing the epic's "Plan ready · needs you" flag** once everything is accepted. Approve plan, which moves it to Ready, clears it as for any ticket. It is listed here in case it gets annoying.
- **The other upstream security companions** (AI/LLM, supply chain, cloud and the rest). Each adds context to every run of the skill. Add one when a project needs it.

## Known risks

- **The gate makes every build run slower** by the project's test time. On the sample repo it adds about 9 s to the worker test suite.
- **The security pass costs tokens.** In the eval, Nancy came in at about $0.10 per review with the skill loaded, against a $0.75 budget. That headroom holds for small diffs; a large diff will cost more.
- **Epic planning on a long doc** reads it in full on Opus, within Plan B's $1.00 budget. A very large doc may hit the budget and land in Blocked; raise the budget or name a section.

## After M4.5: QA checks criteria against a running app (2026-11-05)

Testy no longer reruns the whole suite: the checks gate already ran it before Code Review, and CI reruns it on the PR. QA now answers "does this branch do what the ticket asks?", with evidence per criterion.

- **`start` command** (Settings, `.kanbot/project.yml`). For a QA run the worker starts the app from the worktree on a free `PORT`, waits for any HTTP answer on `/` (60 s), and stops it with its child processes when the run ends (`startApp` in `apps/worker/src/worktree.ts`). An app that won't start goes to Testy as text, not as a run failure.
- **`http_request` tool** on Kanbot's MCP server, only for runs with an app. It reaches only that app: paths, not URLs, no redirects followed (`appRequestUrl` in `fence.ts`). This replaces allowing `curl`, which could reach any host.
- **`<qa_setup>` in the context** tells Testy whether there is a test setup (command and globs) and an app. Without a test setup it doesn't write tests and cites code instead, so a project in a stack the worker can't run still gets a QA pass.
- **Stall detection:** an app request is progress, and a request that changes the app (not GET, HEAD or OPTIONS) resets the repetition count like an edit.
- **The sample repo** has `start: node src/server.ts`.

**Changes to the spec:** §4 Testy's row and "How QA runs" (rewritten); §7 "Project toolchains (required in M5)" and the Isolation note; §8 stall detection rules; §13 Settings; §14 container mode split (project commands in M5, the whole run Later); §16 M5 line and a new first M5 row, the M6 Playwright row; §17 Decided (QA's job, project toolchains); Where things stand.
